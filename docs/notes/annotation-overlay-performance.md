# 画像の上の注釈の印を軽く描く（canvas と DOM の描き分け）

## 2026-10-16

### 何をしたか

注釈が数万件ある画像で、拡大・縮小が重かった。印を 1 件ずつ DOM の要素で描いていたため。
見えている範囲の印の数で、描き方を切り替えるようにした（PR #171、da9fc2b）。

- 見えている範囲の印が 500 個以下（`DOM_MARK_LIMIT`）なら、これまでどおり DOM の印で描く。
  マウスを乗せると注釈名が出て、押すと選べる
- 500 個を超えたら、見えている範囲を 1 枚の canvas にまとめて描く。
  画面の画素の細かさ（devicePixelRatio）に合わせるので、拡大してもぼやけない
- canvas の間も、押した所にある一番小さい印を選ぶ。動かさずに押したときだけ選び、
  ドラッグは画像の移動のまま
- 選んだ印は DOM で canvas の上に重ねる
- 箱が大きいときは canvas の線を 2px にして、DOM の印と太さを揃えた。
  切り替わりの瞬間に線の太さが変わって見えないように
- 注釈 2 万件の資料では、等倍から約 15 倍までが canvas、それより拡大すると DOM になる

場所: `overlays/AnnotationOverlay.tsx`（`AnnotationCanvas`）、
`overlays/annotationMarks.ts`（見えている範囲の計算と当たり判定、テスト付き）。
拡大率の情報（`stage`）は `displays/ImageView.tsx` から `overlays/types.ts` 経由で渡す。

### 測り方

開発モード（`npm run dev`）のブラウザで、ユースケース `suikeichuzu-annotations`
（水経注図、注釈 21,245 件）を開き、拡大を 1 段ずつ進めて、1 段あたりの時間を見た。

### 実測

| | 拡大 1 段あたり |
|---|---|
| 変更前（21,243 個の印がすべて DOM） | 約 330ms |
| 変更後 | ほとんどの段で 4〜15ms |

- canvas の描画そのものは、2 万件で 6ms 以下
- 拡大し始めの 1〜2 段だけ 40〜100ms かかった。タイル画像の読み込みと重なっている時間で、
  そのうち注釈の描画は 6ms 以下だった

### 引き換えに失ったこと

- canvas で描いている間は、印にマウスを乗せても注釈名が出ない
- 印の中に本文を表示する注釈（painted）は、canvas の間は枠だけになる

どちらも、拡大して印が 500 個以下になれば元に戻る。

### 途中で分かったこと

- worktree を新しい main に載せ直したら `npm run gen` を流す。
  生成物が古いままだと、core の export が見つからず tsc が落ちる

### 確かめたこと

- tsc / eslint / vitest（661 件）が通る
- ブラウザで、縮小時の canvas 表示、印を押して選べること、ドラッグで選ばれないこと、
  拡大で DOM の印に戻ることを目で確認した

### 確かめていないこと（限界）

- 本番ビルドでの時間は測っていない。数字はすべて開発モード
- 測ったのは水経注図 1 点だけ。印の大きさの分布が違う資料（小さな印が密集する資料など）では、
  500 個の閾値が適切かは見ていない
- 時間はブラウザで目視した値で、同じ条件で繰り返し測った平均ではない

## 2026-10-16（訂正と測り直し）

### 訂正

上の「測り方」と「限界」の記述は、実際の測り方と違っていた。会話の記録で確かめた。

- 目視ではなかった。ブラウザ（Chrome）の中でスクリプトを流していた。
  画像の中央にホイールの合成イベント（`deltaY` ±300）を 1 回送るのを「拡大 1 段」とし、
  `performance.now()` で時間を取っていた
- 変更前と変更後で、時計を止めた所が違っていた。
  変更前の約 330ms は「`requestAnimationFrame` の中でさらに `requestAnimationFrame`」まで。
  変更後の 4〜15ms は「`requestAnimationFrame` → `setTimeout(0)`」まで。
  変更後を変更前と同じ止め方で測った値は、どの段も 32〜34ms だった
- 拡大し始めの 40〜100ms を「タイル画像の読み込みと重なっている」としたのは推測だった。
  下の測り直しでは、ヘッドレスのときに、縮小側でも同じ時間がかかっている
  （見えている印の数に比例しており、タイルとは関係が薄い）
- ソースの注記（`annotationMarks.ts`）の「1 段 190ms」は、別の回に測った値で、出どころは確かめていない

### 測り方（測り直し）

`scripts/bench/annotation-zoom-bench.mjs`。Playwright 1.63 の Chromium 153 で、
変更前（090f9e8）と変更後（da9fc2b）をそれぞれ本番ビルド（`npm run build` の `out/` を静的に配信）で開く。
画面 1600×1000、画素の細かさ 2 倍。1 回ごとに新しいブラウザコンテキスト（キャッシュ空）で開き、
印が出てから 8 秒待って、拡大 10 段 → 縮小 10 段。段と段の間は 500ms 空ける。
1 段ごとに次を記録した。

- frame1: ホイール → `requestAnimationFrame` → `setTimeout(0)` まで（前回の変更後の止め方）
- frame2: ホイール → `requestAnimationFrame` の中で `requestAnimationFrame` → `setTimeout(0)` まで（前回の変更前の止め方に近い）
- Long Animation Frame（50ms を超えたコマ）の長さと、その内訳（スクリプトと、スタイル計算・レイアウト・塗り）

機械は Apple M4 Max（メモリ 128GB）、macOS 27.0.1。

### 実測（本番ビルド、画面を出したブラウザ、3 回 × 20 段）

| | frame1 中央値 | frame2 中央値 | 50ms を超えたコマがあった段 |
|---|---|---|---|
| 変更前（印 21,243 個がすべて DOM） | 251ms | 258ms | 60 段中 60 段 |
| 変更後・canvas の段（拡大率 約 15 倍まで） | 9ms | 16ms | 39 段中 1 段（110ms） |
| 変更後・DOM の段（見えている印 10〜228 個） | 3ms | 16ms | 21 段中 0 段 |

- 変更前の 1 コマの内訳は、スクリプト約 20ms、スタイル計算・レイアウト・塗り約 180ms。
  重さはほとんどブラウザの描画の側にあった。印の線の太さを `calc(2px / var(--image-scale))` で
  決めているので、拡大率が変わるたびに 2 万個すべての計算と塗り直しが起きる
- 変更後の frame2 の 16ms は 1 コマ分の待ち時間そのもので、作業の時間は測れていない
- 拡大し始めの 2 段も、変更後は 18ms（中央値）だった

### 途中で分かったこと

- ヘッドレスの Chromium では、変更後の canvas の段が見えている印の数に比例して遅くなった
  （拡大率 1〜2.5 倍で 70〜128ms、6 倍で約 25ms）。画面を出したブラウザでは同じ段が 16ms 前後。
  canvas の塗りの速さが、ヘッドレスかどうか（おそらく GPU を使うかどうか）で大きく変わる。
  ヘッドレスの数字で canvas の速さを判断しない
- 開発モード（`next dev`）で同じ測定をすると、変更前は約 550ms（スクリプト約 240ms ＋ 描画約 240ms）、
  変更後も縮小しきった canvas の段で 110〜260ms（ほぼスクリプト）になった。
  React の開発用の検査が重く、変更の効果を見る数字には向かない。前回の数字（開発モード）とも合わない

### 確かめていないこと（限界）

- 測ったのは水経注図 1 点と、この機械 1 台だけ
- ヘッドレスで canvas が遅くなる理由（GPU の有無）は推測で、確かめていない
- 前回の開発モードの数字（330ms、4〜15ms）を再現できなかった理由は調べていない

## 2026-10-16（訂正 2）

記事にする前の点検で、上の測り直しの数字に 2 つの取り違えがあった。測り直しの出力を集計し直して確かめた。

- 変更前の frame2 中央値 258ms は、拡大し始めの 2 段を除いた値だった。
  全 60 段の中央値は 260.6ms（約 261ms）。表の他の行（変更後）は、除いた段を別に書いているので変わらない
- 開発モードの変更前「約 550ms」は、frame2 の中央値ではなかった。frame2 の中央値は 569ms（約 570ms）。
  「スクリプト約 240ms ＋ 描画約 240ms」は、50ms を超えたコマ（Long Animation Frame）の内訳で、frame2 の内訳ではない
- 結論（変更前は描画が重く、変更後は 1 コマで済む）は変わらない
